### 2-1-k. 2026-08-18 종목별 개별 승률 (사용자 지시)

### 2-1-l. 2026-08-18 종목별 승률 표본 늘리기 — 1년 백테스트 (사용자 지시)

**계기** — 종목별 승률이 대부분 '표본 부족'(1~5건)이라 사용자가 물었다:
"예전 1년치 원장 있으면 딱 한 번만 조회해서 쓰면 안 되나?"

**사실 확인** — 1년치 원장은 **없다**(history/는 8/07부터, hist는 30행).
다만 `main.py`가 매 실행마다 야후에서 **1년치를 받아 최근 30일만 쓰고 버린다.**
그 버리는 부분을 한 번만 살리면 된다.

**제약** — `analyze()`는 `len(close) >= 61 + HIST_DAYS`, `market_state()`는
`66 + HIST_DAYS`를 요구한다. 야후 1년 ≈ 252봉이므로 **HIST_DAYS 상한은 186**.
180으로 잡으면 지금의 6배다. main.py는 한 줄도 고치지 않는다.

**구현 (3개)**
| 파일 | 역할 |
|---|---|
| `tools/backfill_backtest.py` | main의 `analyze()`·`market_state()`를 **그대로** 쓰되 HIST_DAYS만 180으로. `backtest/raw.json`(~5MB) 생성 |
| `tools/ticker-record-build.js` | raw + index.html의 `evaluate()` 추출 → `backtest/ticker-record.json`(~10KB) |
| `.github/workflows/backtest-ticker-record.yml` | 수동 실행. raw는 커밋하지 않고 요약만 커밋 |

사이트는 `loadTickerBacktest()`로 이 파일을 읽고, 있으면 백테스트 숫자를,
없으면 기존 원장 30일 계산을 쓴다. 로드 실패해도 사이트는 그대로 뜬다.

**⚠ 반드시 지킬 것 — 이건 원장이 아니다**
- `signals.json`·`history/`는 이 워크플로우가 **쓰지 않는다.** 워크플로우 안에

- 화면에도 빨간 글씨로 적는다: **소급 적용 · 생존 편향**.

  검증표(원장 30거래일)와 **직접 비교 금지**.
- 파일 안에도 `kind:"backtest"` · `survivorship_warning` · `earnings_excluded`를
  넣어, 나중에 이 파일만 보고도 성격을 알 수 있게 했다.

**2026-08-18 보강 — "실적영향이랑 필터 싹다 적용된거 맞지?" (사용자 확인 요청)**

## 4. 작업 규칙 (요약 — 자세한 건 방법론 문서)

1. **산식을 다시 짜지 마라.** 검증 스크립트는 index.html에서 함수를 문자열로
   추출해 쓴다(`tools/*.js` 전부 이 방식). 두 곳에 두면 반드시 어긋난다.
2. **승률만 보지 마라.** 반드시 같은 구간 기준선 대비 %p로. 컷을 걸 때는
   "지워지는 표본의 성적"을 따로 찍어라 — 승률이 올라도 지운 게 승자 집단이면 착시다.
3. **표본 기준**: 50+ 조정 가능 / 30~50 방향만 / 15~30 참고 / 15 미만 신뢰 불가.
   같은 종목·날짜 겹치면 유효 표본 절반 이하.
4. **과거 hist는 절대 수정 금지** (append-only). hist_fields는 꼬리 추가만 허용.
5. 전·후반 반으로 갈라 양쪽 다 기준선을 넘어야 채택. 한쪽만 좋으면 장세 잔상.
6. 레버리지 상품 판정은 1배 환산(levX 나누기)이 기본.

```
node tools/formula-lab.js      # 추세·반등 게이트 변형 비교 (대조군 P0 = 현재 배포값)
```
